2. Comprensión del Patrón (API Gateway & Load Balancing)

  1. Punto Único de Contacto: El cliente externo solo se comunica con localhost:18080. Se abstrae completamente la topología de la red interna.
  2. Resolución de Esquema lb://: Cuando el Gateway recibe una petición en /api/ordenes, busca el predicado coincidente y lee el destino lb://pagatu-orden-ms. El prefijo lb:// instruye a Spring Cloud LoadBalancer que consulte a Eureka para obtener la lista viva de instancias.
  3. Algoritmo Round Robin: El balanceador distribuye las peticiones secuencialmente por turnos: la primera va a la instancia 1 (8082) y la segunda a la instancia 2 (8083).
  4. Tolerancia a Fallos Transparente: Si una réplica se apaga, Eureka expira su heartbeat y el Gateway redirige el 100% del tráfico a las réplicas sanas restantes.

3. Error o Hallazgo Diagnosticado

Descripción del Problema: Al compilar pagatu-gateway, la aplicación arrojaba error de casteo entre ApplicationContext reactivo y de Servlets.

Causa Raíz: Spring Cloud Gateway es no bloqueante y reactivo sobre Netty. La inclusión inadvertida de spring-boot-starter-web crea un conflicto con Tomcat embebido.

Solución Implementada: Se configuró el pom.xml exclusivamente con spring-cloud-starter-gateway y librerías reactivas, permitiendo la inicialización limpia en el puerto 18080.

4. Reflexión Técnica Breve

¿Por qué agregar un microservicio nuevo al sistema no debería exigir que los clientes existentes cambien nada de su configuración?

El principio de desacoplamiento arquitectónico dicta que los consumidores de una API no deben estar acoplados a la infraestructura interna del proveedor. Gracias al API Gateway, los clientes externos únicamente conocen la URL base pública (http://gateway:18080). Cuando el equipo incorpora un nuevo microservicio (por ejemplo, pc-pago-ms para procesar cobros de hardware con Mercado Pago), únicamente se registra una nueva regla de enrutamiento en config-repo/pagatu-gateway-dev.yml. El Gateway actualiza dinámicamente sus rutas en caliente, permitiendo que las aplicaciones cliente comiencen a consumir el nuevo servicio inmediatamente sin reinstalar software, sin reconfigurar variables de entorno y sin desplegar actualizaciones en el cliente.

5. Preguntas de Defensa

  1. ¿Por qué lb://pagatu-catalogo-ms no es una dirección real, y quién la resuelve?
    Es un esquema lógico resuelto por Spring Cloud LoadBalancer consultando a Eureka por el Service ID.
  2. ¿Qué diferencia hay entre un Path que no coincide y un servicio caído?
    Path no coincidente retorna 404 Not Found; servicio caído retorna 503 Service Unavailable o 504 Gateway Timeout.
  3. ¿Por qué dos recursos del mismo microservicio necesitan dos rutas distintas?
    Porque el enrutamiento se basa en coincidencia de patrones (Path), permitiendo aplicar filtros o políticas específicas a cada recurso.
  4. Si detienes una instancia con Ctrl+C, ¿cuánto tiempo pasa hasta que el Gateway deja de enviarle tráfico?
    Entre 30 y 90 segundos, determinado por el intervalo de heartbeat y la expiración del arrendamiento en Eureka.
  5. ¿Por qué agregar la ruta de pagatu-orden-ms no requirió tocar ninguna configuración de pagatu-catalogo-ms?
    Porque los microservicios son autónomos y el Gateway maneja las rutas de forma modular e independiente.
