1. Resumen de Arquitectura del Sistema Distribuido Base

El ecosistema distribuido de ChaskiPC integra un punto único de acceso (Gateway en puerto 18080 DEV / 28080 PROD), un registro de servicios Eureka (8761 DEV / 28761 PROD), configuración centralizada por ambiente (8888 DEV / 28888 PROD), microservicios de catálogo y órdenes con ejecución concurrente y persistencia relacional en PostgreSQL (puerto 5433).

2. Balotario de Sustentación Teórico-Práctica (S1 a S4)

1. ¿Por qué tu microservicio no debería depender de un puerto fijo asignado a mano, y cómo verificaste que corre con múltiples instancias en paralelo?
Depender de un puerto fijo impide el escalado horizontal. Al usar instance-id: ${spring.application.name}:${server.port} con Eureka, el microservicio se anuncia dinámicamente. Se verificó arrancando una instancia en 8082 y otra en 8083; ambas se muestran vivas simultáneamente en Eureka (UP (2)) y atienden peticiones concurrentes compartiendo PostgreSQL.

2. ¿Qué diferencia hay entre una propiedad fija en el código y una leída desde tu Config Server, y por qué esa diferencia importa entre DEV y PROD?
Una propiedad fija exige recompilar el JAR ante cualquier cambio. Con Config Server, las configuraciones residen en config-repo: en DEV se usa la BD local con logs DEBUG y DDL update; en PROD se inyectan credenciales seguras y DDL validate, cumpliendo con el Factor III de los 12 Factores sin tocar el código.

3. Si detienes una instancia de tu servicio, ¿cómo se entera tu registro de que ya no está disponible, y por qué no es instantáneo?
El microservicio envía un heartbeat cada 30s. Si se apaga, Eureka espera la ventana de expiración del arrendamiento (90s) antes de desalojarla del catálogo. Esto previene que caídas momentáneas de red expulsen servicios sanos de forma prematura.

4. ¿Por qué la dirección lb:// no es una dirección real, y qué componente la resuelve?
lb:// es un esquema lógico de Spring Cloud LoadBalancer. No es una IP ni un DNS. El LoadBalancer consulta a Eureka para obtener la lista física de instancias vivas y enruta la petición hacia una de ellas.

5. ¿Qué algoritmo de balanceo usa tu Gateway por defecto, y por qué es suficiente para instancias sin estado?
Usa Round Robin. Es suficiente porque las instancias son idénticas y stateless; todo el estado vive en la base de datos PostgreSQL compartida, garantizando equidad de carga sin necesidad de afinidad de sesión.

4. Bitácora de Despliegue DevOps: Resolución de los 7 Desafíos Técnicos de Portabilidad (DTI-Laboratorio)

Al migrar el ecosistema distribuido a los equipos del laboratorio universitario (DTI-Laboratorio), se identificaron y solucionaron 7 problemas técnicos clásicos de portabilidad y dependencias:

1. Rutas Absolutas Quemadas (Hardcoded Paths)

Diagnóstico: El script original fallaba porque buscaba C:\Users\USUARIO\Documents\Tarea Eureka\....
Causa: Acoplamiento rígido de rutas al usuario inicial.
Solución: Refactorización dinámica con rutas relativas basadas en os.path.dirname(os.path.abspath(__file__)) y Split-Path -Parent $MyInvocation.MyCommand.Path, haciendo el proyecto 100% portable a cualquier máquina o USB.

2. Ausencia del Intérprete de Python

Diagnóstico: El archivo .bat no reconocía el comando python.
Causa: La máquina del laboratorio no tenía Python en sus variables de entorno del sistema.
Solución: Se instaló con winget install Python.Python.3.12 y se creó el lanzador nativo iniciar_todo.ps1 en PowerShell puro (cero dependencias de Python), adaptando el .bat para autodetectar y ejecutar el script adecuado.

3. Conflicto de Versiones de Java (release version 21 not supported)

Diagnóstico: Maven fallaba indicando incompatibilidad con Java 21.
Causa: JAVA_HOME apuntaba a un JDK 17 preinstalado, a pesar de que el JDK 21 estaba instalado en el disco.
Solución: Se actualizó la variable de entorno con setx /M JAVA_HOME "..." y se añadió autodetección de JDK 21 en los scripts para inyectar $env:JAVA_HOME en cada ventana de PowerShell.

4. Conflicto de Sintaxis y Comillas en PowerShell (Instancia 2)

Diagnóstico: Error de Maven: Unknown lifecycle phase ".run.arguments=--server.port=8083".
Causa: PowerShell fragmentaba el argumento debido a las comillas dobles anidadas de -Dspring-boot.run.arguments.
Solución: Se reemplazó por la variable de entorno estándar de Spring Boot: $env:SERVER_PORT = '8083'; .\mvnw.cmd spring-boot:run.

5. Config Server Desconectado del Repositorio (DataSource url is not specified)

Diagnóstico: pagatu-orden-ms no arrancaba por falta de configuración de base de datos.
Causa: search-locations en pagatu-config apuntaba a la ruta estática de la PC anterior, entregando configuraciones vacías.
Solución: Se parametrizó application.yml con ${CONFIG_REPO_PATH:file:../config-repo} y se inyectó la ruta absoluta calculada dinámicamente desde el script de arranque.

6. Servidor de PostgreSQL Apagado (Connection refused: localhost:5433)

Diagnóstico: Conexión rechazada en localhost:5433.
Causa: Los contenedores Docker de Postgres existían pero estaban en estado detenido (Exited).
Solución: Se creó infra/docker-compose-db.yml y el script iniciar_db.bat para arranque y supervisión automática del contenedor chaskipc-db-orden.

7. Credenciales y Usuario de Base de Datos (password authentication failed for user "admin")

Diagnóstico: PostgreSQL rechazaba la autenticación del usuario admin.
Causa: El contenedor en el laboratorio fue inicializado con usuario postgres y clave password123, mientras que el proyecto requiere usuario admin, clave adminpassword y BD orden_db.
Solución: Se ejecutaron sentencias SQL para crear el usuario admin, otorgar permisos y se declararon formalmente en docker-compose-db.yml.
