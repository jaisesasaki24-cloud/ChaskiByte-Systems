2.4 Arquitectura del Sistema Distribuido Base

Ecosistema cloud-native con punto de entrada único, descubrimiento dinámico y persistencia segregada:

🚪 API Gateway (:18080)

Spring Cloud Gateway reactivo (WebFlux/Netty). Único puerto expuesto para clientes externos. Resuelve rutas lb:// con Round Robin.

🧭 Eureka Registry (:8761)

Netflix Eureka Server. Gestiona el registro dinámico de microservicios mediante latidos periódicos (heartbeats cada 30s).

⚙️ Config Server (:8888)

Spring Cloud Config Server centralizado. Lee perfiles desde config-repo desacoplando la configuración del código fuente.

🛒 Microservicios ChaskiPC

  • Catálogo Hardware (:8081): Categorías y Productos con stock y datos técnicos.
  • Órdenes Transaccional (:8082 y :8083): Dos instancias simultáneas con modelo Cabecera-Detalle e IGV 18%.

📊 Base de Datos y Observabilidad

  • PostgreSQL (:5433): Persistencia física compartida (orden_db).
  • Prometheus + Grafana + Loki: Scrape automático con Eureka Service Discovery y logs centralizados.

2.1 y 2.2 Alcance de Servicios y Contrato REST

El sistema cuenta con un microservicio no transaccional y uno transaccional con respuestas HTTP estandarizadas:

Microservicio Método Endpoint (vía Gateway :18080) Códigos HTTP Descripción
Catálogo Hardware
(No transaccional)		 GET /api/v1/categorias 200 OK Lista categorías (CPUs, GPUs, RAM, Almacenamiento).
GET / POST /api/v1/productos 200 OK / 201 Created Consulta de hardware con stock y alta de nuevos componentes.
Órdenes ChaskiPC
(Transaccional)		 GET /api/v1/ordenes 200 OK Lista general de órdenes balanceada equitativamente.
POST /api/v1/ordenes 201 Created / 400 Bad Request Crea orden con ítems, comprobante y desglose de IGV (18%).
GET /api/v1/ordenes/{id} 200 OK / 404 Not Found Búsqueda por ID con validación de recurso no encontrado.

💡 Semilla de Datos Automática: Ambos microservicios incorporan DataInitializer. Arrancan en cualquier máquina con productos de hardware y órdenes de prueba precargadas automáticamente.

2.3 Configuración por Ambiente (DEV vs PROD)

Aplicación estricta del Factor III (The Twelve-Factor App) mediante config-repo:

Ambiente DEV pagatu-orden-ms-dev.yml

  • Puerto: 8082 / 8083 en host local.
  • Base de Datos: PostgreSQL en localhost:5433/orden_db.
  • Hibernate: ddl-auto: update para desarrollo ágil.
  • Logs: Nivel detallado y escritura en ../logs/*.log.
  • Actuator: Endpoints abiertos para monitoreo (Prometheus, Health).

Ambiente PROD infra/compose.yml

  • Puerto Gateway: 28080 (único puerto expuesto al host).
  • Red Aislada: Red interna cerrada de Docker (pagatu-prod-net).
  • Hibernate: ddl-auto: validate (prohíbe alterar tablas).
  • Seguridad: Credenciales inyectadas por variables de entorno seguras.
  • Config Server: Puerto 28888 y Eureka en 28761.

Principio Clave: Se compila un único archivo .jar y el ambiente determina su comportamiento sin modificar ni una sola línea de código fuente.

Bitácora DevOps: Resolución de los 7 Desafíos de Laboratorio

Soluciones de ingeniería implementadas para garantizar la portabilidad en equipos de laboratorio:

Desafíos de Entorno y Rutas

  • 1. Hardcoded Paths: Resuelto con rutas relativas dinámicas en Python y PowerShell.
  • 2. Falta de Python: Creado lanzador nativo iniciar_todo.ps1 en PowerShell puro.
  • 3. Conflicto Java 17/21: Autodetección de JDK 21 e inyección forzada de $env:JAVA_HOME.
  • 4. Comillas en PowerShell: Reemplazo por $env:SERVER_PORT='8083' nativo.

Desafíos de Configuración y Docker

  • 5. Config Server Vacío: Fallback dinámico con ${CONFIG_REPO_PATH:file:../config-repo}.
  • 6. PostgreSQL Apagado: Script iniciar_db.bat en puerto 5433 para evitar colisiones con el 5432.
  • 7. Credenciales rechazadas: Estandarización de usuario admin y clave adminpassword.

🛡️ Script Preventivo para Grupo 4: limpiar_pc_laboratorio.bat libera en 3 segundos los puertos ocupados por grupos anteriores antes de iniciar.

3. Evaluación Teórico-Práctica (Balotario Clave)

¿Por qué no depender de puertos fijos?

Un puerto fijo impide el escalado horizontal. Usando instance-id: ${spring.application.name}:${server.port} con Eureka, los nodos son efímeros y escalables dinámicamente.

¿Config Server vs Propiedad en Código?

Permite segregar ambientes (DEV/PROD) sin recompilar el artefacto binario JAR, cumpliendo el Factor III de The Twelve-Factor App.

¿Por qué el desalojo en Eureka no es inmediato?

Evita el flapping (inestabilidad por latencia transitoria). Eureka espera 30s de latido y 90s de expiración de arrendamiento antes de desalojar.

¿Qué es el esquema lb:// y quién lo resuelve?

Es un URI lógico de Spring Cloud LoadBalancer. El filtro reactivo del Gateway lo resuelve consultando las instancias vivas en la memoria de Eureka.
